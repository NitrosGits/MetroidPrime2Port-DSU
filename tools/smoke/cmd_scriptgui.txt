# ScriptGui (module 60: CScriptGuiScreen/Menu/Widget/Slider ... the front end's GWIG/GMNU/GSLD/GSCR
# script objects - the menus, widgets and sliders that draw and drive the front end screens).
# FrontEnd (world 69802220, area cee3af0d), which the run boots with SKIP_FRONTEND=0: with the front
# end skipped the FrontEnd area never loads and the script objects never appear. Its object ids are
# the area's short editor ids, e0 (the front end screen) and e2ab / e21c / e245 (menu, slider,
# widget), so a driver has to drive only a few of them - the area boots at about 1008/1024 object
# ids, and mass activation exhausts the pool (docs/module-analysis/ScriptGui.md).
# The steps repeat the gui1 lane's tools/cov/specs/gui_menu_slider.con: `send e0 Unlock` first
# (without it StartSelectedGame faults on a null save screen), the menu's Activate/Alert and its
# forced Open/Close/Lock/Unlock arms, the four menu pads' presses (down/up four times each, the
# wrap arms), SetToMax/SetToZero and the three InternalMessages, the x/y/z/start presses, the
# Follow message, then the slider e21c: Activate/Alert, Increment/Decrement, a held right and a held
# left `press`, Deactivate and Activate again, and its Delete - with `objs Gui` before the steps and
# `obj` reads of the menu and slider around them.
# Evidence in the transcript: `objs Gui` listing the area's CScriptGui objects (the front end
# screen, the menus and the slider) before the driver sends anything, `obj e2ab` and `obj e21c`
# reading each object's state and message map (the menu's Open/Close/Lock/Unlock and the slider's
# Increment/Decrement/SetToMax/SetToZero arms), every `send` and `press` answering `=> ok` with the
# object it reached (`sent Activate to u0674 000002ab`), and the slider's Delete dropping the list
# from 133 objects at f130 to 132 at f600 - that count is the Delete's check (an `obj e21c` after it
# could only answer "no object with editor id", which con.py reports as a step error). The log's
# `init compiled module ScriptGui` line lists the whole compiled-module table, so it says the module
# is registered, not that it ran.
# Checks are game updates (@f<n>), never wall seconds. The area boots at about 1008/1024 object ids,
# so the steps stay the driver's own few objects and its late checks are `obj` (a forced menu state
# and message map - stable) rather than an `objs` list of moved positions. F=700, last check f600.
